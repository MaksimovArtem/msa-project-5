# ADR-004: Мониторинг, централизованное логирование и оповещение Spring Batch-приложения

<a name="_hjk0fkfyohdk"></a>**Автор: Максимов Артем**

## 1. Контекст

В проекте используется короткоживущее `Spring Batch`-приложение:
- job запускается при старте контейнера
- обрабатывает CSV-данные
- записывает результат в `PostgreSQL`
- после завершения корректно завершает процесс
## 2. Требования

Для такого типа приложения нужно решить задачи:
1. собирать технические и бизнес-метрики выполнения batch-job
2. собирать структурированные логи приложения и централизованно хранить их
3. настроить работающее оповещение о сбоях, деградации и потере наблюдаемости

Главное архитектурное ограничение состоит в том, что приложение не является постоянно работающим HTTP-сервисом. Из-за этого классическая pull-модель Prometheus напрямую с контейнера приложения нестабильна: приложение может завершиться раньше, чем Prometheus успеет выполнить scrape

## 3. Решение

Принято следующее архитектурное решение:
- для метрик использовать `Pushgateway` как промежуточную точку приёма метрик short-lived batch-приложения
- для хранения и обработки метрик использовать `Prometheus`
- для визуализации использовать `Grafana`
- для централизованного логирования использовать `ELK`-стек:
	- `Filebeat`
	- `Logstash`
	- `Elasticsearch`
	- `Kibana`
- для alerting использовать `Prometheus Alert Rules`

### Почему `Pushgateway`

`Pushgateway` выбран потому, что:
- приложение завершается сразу после выполнения job
- метрики должны сохраняться после завершения контейнера

### Почему `Prometheus` для alerting
`Prometheus` выбран для оповещений потому, что:
- alert-правила хранятся как код в репозитории
- выражения строятся прямо по тем же сериям, что используются в дашбордах
- alert-состояния дополнительно доступны через метрику `ALERTS`

### Почему `ELK`

`ELK` выбран для логирования потому, что:
- приложение пишет структурированные JSON-логи в `stdout`
- `Filebeat` читает docker-логи контейнера
- `Logstash` принимает и проксирует события в `Elasticsearch`
- `Kibana` позволяет демонстрировать поиск и анализ логов без дополнительной ручной настройки
## Реализованные ключевые метрики

В проекте реализованы и публикуются следующие batch-метрики:

- `spring_batch_completed_job_count_total` - Общее количество успешных выполнений job
- `spring_batch_failed_job_count_total` - Общее количество неуспешных выполнений job
- `spring_batch_last_job_duration_ms` - Длительность последнего выполнения job в миллисекундах

Дополнительно для контроля доставки метрик используются системные метрики `Pushgateway`, в частности:
- `push_time_seconds`
- `push_failure_time_seconds`
- `up{job="pushgateway"}`
## Что отображается на дашборде

Дашборд в `Grafana` предназначен для быстрой оценки состояния batch-приложения и показывает:
- доступность `Pushgateway`
- число успешных и неуспешных запусков
- длительность последнего выполнения job
- возраст последних успешно отправленных метрик
- текущее состояние alert-правил Prometheus
## Реализованные данные логирования

Приложение пишет структурированные JSON-логи. Для поиска и анализа в `Kibana` используются следующие ключевые поля:
- `app` - Имя приложения, например `batch-processing`
- `ts` - Временная метка события
- `level` - Уровень логирования
- `logger` - Имя logger’а
- `class` - Java-класс, из которого пришло сообщение
- `method` - Метод, из которого пришло сообщение
- `file` - Имя исходного файла
- `line` - Номер строки
- `thread` - Имя потока
- `msg` - Основное текстовое сообщение
- `trace`, `span`, `parent` - Поля трассировки, если контекст был передан

Также в `Elasticsearch` сохраняются docker-метаданные:
- `container.name`
- `container.image.name`
- `host.name`
- `stream`
## Какие события логируются

Для сценария batch-наблюдаемости наиболее важны следующие типы событий:
- старт job
- завершение job со статусом и длительностью
- старт step
- завершение step с `readCount`, `writeCount`, `commitCount`, `rollbackCount`, `skipCount`
- сообщения процессора о трансформации данных
- итоговые сообщения о данных, записанных в `PostgreSQL`
- сообщения об успешной или неуспешной отправке метрик в `Pushgateway`

Примеры полезных сообщений:
- `spring-batch job started`
- `spring-batch step finished`
- `spring-batch job finished`
- `batch metrics pushed to Pushgateway`
## Реализованные оповещения

В проекте настроены три основных alert-правила:
### `SpringBatchJobFailuresDetected`

Срабатывает, если за последние 15 минут появился хотя бы один неуспешный job-run.
Назначение:
- обнаружение функциональных ошибок batch-процесса
- быстрое выявление неуспешных повторных запусков

### `SpringBatchJobExecutionTooSlow`

Срабатывает, если длительность последнего выполнения job превышает 30 секунд.
Назначение:
- обнаружение деградации производительности
- контроль роста времени обработки
### `SpringBatchMetricsMissing`

Срабатывает, если `Pushgateway` не получал свежие метрики более 10 минут.
Назначение:
- контроль потери наблюдаемости
- обнаружение проблем с push метрик или отсутствия новых batch-запусков

## Последствия решения

### Положительные
- архитектура подходит для короткоживущего batch-приложений
- метрики доступны после завершения контейнера приложения
- alerting и dashboards описаны как код
- логи централизованы и доступны через `Kibana`
- есть единая картина по метрикам, логам и статусу batch-run
### Компромиссы

- `Pushgateway` добавляет отдельный компонент в инфраструктуру
- в учебном проекте стек получается тяжелее, чем минимально необходимый
- для корректной интерпретации `SpringBatchMetricsMissing` нужно учитывать частоту запусков job
