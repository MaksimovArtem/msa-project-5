# ADR-001: Выбор решения для пакетной обработки данных отдела маркетинга

 <a name="_hjk0fkfyohdk"></a>**Автор: Максимов Артем**
## 1. Контекст

Маркетинговому отделу требуется расширенная пакетная обработка клиентских данных из разных источников:

- CSV-файлы из файлового хранилища со статусами доставок;
- таблицы PostgreSQL с заказами;
- Kafka-события с историей модификации заказов.

Текущая система не справляется с поставленной задачей
## 2. Требования

Необходимо выбрать технологическое решение, которое позволит:
- гибко описывать pipeline
- интегрироваться с
	- внешними API
	- BigQuery
	- Redshift
	- Kafka
	- Spark
	
- Поддерживать 
	- мониторинг
	- оповещения 
	- retry-политики
	- условную логику

Система должна обрабатывать до миллиона записей за один прогон пайплайна
Система должна быть развертываема в облаке

## 3.  Критерии выбора решения

Для сравнения технологических решений были выбраны пять основных критериев:

1. **Интеграции с источниками и внешними системами.**  
   Решение должно иметь готовые механизмы интеграции с CSV/file storage, PostgreSQL, Kafka, BigQuery, Redshift, Spark и внешними API. Это снижает объём custom-разработки и ускоряет внедрение.

2. **Гибкость pipeline и поддержка условий.**  
   Решение должно позволять описывать pipeline как набор связанных шагов, поддерживать зависимости, ветвление, условную логику и запуск по событиям.

3. **Надёжность выполнения.**  
   Решение должно поддерживать retry-политики, fallback-логику, обработку ошибок, callbacks и отправку email-уведомлений при успешном или неуспешном завершении pipeline.

4. **Масштабируемость и модель обработки данных.**  
   Решение должно быть применимо для обработки около 1 млн записей за запуск и позволять выносить тяжёлые вычисления во внешние системы, такие как Spark, BigQuery или Redshift.

5. **Эксплуатация и cloud-ready развёртывание.**  
   Решение должно иметь средства мониторинга, логирования, историю запусков, Web UI и понятный путь развёртывания в облачной инфраструктуре, например через Kubernetes, Helm или managed-сервис.
## 4.  Решение

### 4.1 Описание

Использовать решение на базе Apache Airflow
### 4.2 Соответствие критериям

#### Интеграции с источниками и внешними системами  
  
Airflow имеет развитую систему provider-пакетов. Например, `apache-airflow-providers-postgres` для Postgres
CSV-файлы можно обрабатывать через Python-задачи
#### Гибкость pipeline и поддержка условий  
  
Airflow описывает pipeline как DAG — направленный ациклический граф задач.  pipeline as code.
  
Это позволяет:  
- задавать зависимости между шагами;  
- переиспользовать задачи;  
- параметризовать запуски;  
- строить разные ветки выполнения;  
- запускать pipeline по расписанию или вручную.  
  
#### Надёжность выполнения  
  
Airflow поддерживает основные механизмы надёжного выполнения из коробки. Например `retries` для повторного выполнения и `EmailOperator` для отправки письма
Fallback-логику можно реализовать через отдельные задачи, которые запускаются при ошибке основной ветки
  
#### Масштабируемость и модель обработки данных  
  
Airflow подходит для оркестрации обработки объёма около 1 млн записей за запуск
#### Эксплуатация и cloud-ready развёртывание  
  
Airflow подходит для развёртывания в облаке. Его можно развернуть в k8s и хостить на облаках например в Google Cloud Composer или AWS
  
Для удобства эксплуатации предоставляет:   
- Web UI;  
- историю запусков;  
- статусы DAG и задач;  
- логи выполнения  
## 5. Альтернативы

### 5.1 Apache NiFi

Apache NiFi рассмотрен как альтернатива для визуального построения data flow. Он закрывает критерий интеграций с источниками и внешними системами. У него есть готовые процессоры для файлов, HTTP API, Kafka и баз данных. В плане надежности не уступает Airflow

Однако для данного кейса NiFi менее удобен, чем Airflow. Его сильная сторона — визуальная маршрутизация и доставка данных, но сложные batch-пайплайны с условиями, бизнес-ветвлениями, fallback-сценариями и отчётными шагами проще описывать в виде Airflow DAG. Кроме того, Airflow лучше подходит для подхода pipeline as code: пайплайны проще хранить в Git, ревьюить, тестировать и разворачивать через CI/CD

### 5.2 Prefect

Prefect хорошо поддерживает гибкость пайплайнов и условия: ветвления, параметры и динамическая логика описываются в Python-коде. По надёжности выполнения Prefect тоже закрывает базовые требования: есть retries, состояния задач, обработка ошибок и уведомления.

Имеет менее зрелую инфраструктуру, чем Airflow, но позволяет гибко работать за счет того что все описано через Python
