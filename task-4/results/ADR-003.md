# ADR-003: Технология для ETL

 <a name="_hjk0fkfyohdk"></a>**Автор: Максимов Артем**
## 1. Контекст

TradeWare обрабатывает данные по остаткам и перемещениям товаров, поступающие от складов. Обработка выполняется внутри Java-монолита в онлайн-сценарии: пользователь загружает файл через ERP-интерфейс и ждёт окончания обработки

Текущая архитектура создаёт несколько проблем:

- обработка файла выполняется синхронно и блокирует пользователя на продолжительное время;
- данные обновляются построчно, а не блоками;
- тяжёлая обработка конкурирует с онлайн-запросами ERP и API;
- нет нормального механизма retry/restart;
- сложно понять, на каком этапе произошла ошибка

Компания использует: 
- Java 11
- PostgreSQL
- GCS
- Docker/Docker Compose
- GCP
## 2. Требования

Требуется подготовить систему к будущему увеличению количества пользователей:

1. Обеспечение надёжной работы под возрастающей нагрузкой. 
	Предполагаемая нагрузка — 100–150 параллельных загрузок в пиковые часы. 
2. Возможность гибко масштабироваться под нагрузкой
3. SLA: среднее время обработки отчёта на 2 000 строк составляет до 30 секунд
4. Внедрение системы централизованного сбора логов и метрик
5. Подготовить архитектуру к постепенной миграции на микросервисы
6. Сохранить хорошую интеграцию с Java-экосистемой
## 3.  Критерии выбора решения

|Критерий|Описание|
|---|---|
|Производительность|Обработка данных блоками, а не построчно|
|Масштабируемость|Возможность масштабировать обработчики независимо от монолита|
|Надёжность|Retry, restart, обработка частичных ошибок|
|Интеграция|Совместимость с Java, PostgreSQL, GCS|
|Наблюдаемость|Метрики, логи, статусы job|
|Микросервисная миграция|Возможность вынести ETL в отдельный сервис|
|Простота запуска|Локальное развёртывание через Docker Compose|
|Расширяемость|Возможность добавлять новые шаги pipeline|
## 4.  Решение

Выбрать Spring Batch как технологию для ETL-обработки складских CSV-отчётов.

Spring Batch предлагается внедрить как отдельный компонент — Batch Processing Service, развёрнутый рядом с текущим Java-монолитом.
C4 диаграмма представлена в C4.jpg
### 4.1 Описание

С монолита снимается задача синхронной обработки файлов. Он продолжает отвечать за следующий сценарий:

1. принять CSV-файл
2. выполнить первичную проверку
3. сохранить файл в GCS
4. создать запись о загрузке
5. запустить batch job
6. показывать пользователю статус обработки не занимая процесс пользователя

Новый сервис берет на себя задачу ETL:

1. прочитать CSV из GCS
2. провалидировать строки
3. обогатить даннымы из БД справочных данных
4. записать данные в БД блоками
5. сохранить ошибки обработки

Описанный пайплайн должен быть покрыт метриками и логами

Данные предлагается хранить в PostgreSQL с логическим разделением по назначению:

| Группа данных         | Для чего используется                                    |
| --------------------- | -------------------------------------------------------- |
| Spring Batch metadata | Хранение служебной информации о выполнении job и step    |
| Upload jobs           | Отслеживание бизнес-статусов загруженных файлов          |
| Staging tables        | Временное размещение данных перед финальной обработкой   |
| Result tables         | Хранение актуальных данных по остаткам товаров           |
| Processing errors     | Фиксация ошибок, найденных при обработке отдельных строк |

### 4.2 Соответствие критериям

| Критерий                | Решение                                                      |
| ----------------------- | ------------------------------------------------------------ |
| Производительность      | Поддерживает работу блоками                                  |
| Масштабируемость        | Можно запускать несколько batch-worker’ов                    |
| Надёжность              | Есть restart, retry, skip policy                             |
| Интеграция              | Хорошо интегрируется с Java-стеком, PostgreSQL и Spring Boot |
| Наблюдаемость           | Интегрируется с Micrometer и Prometheus                      |
| Микросервисная миграция | ETL-логику можно вынести из монолита                         |
| Простота запуска        | Легко поднимается в Docker Compose                           |
| Расширяемость           | Pipeline расширяется через новые Step                        |
## 5. Альтернативы

### 5.1 Apache Airflow

Apache Airflow — это оркестратор batch/data pipeline. Он подходит для управления сложными цепочками задач, расписаниями, зависимостями и повторными запусками.

| Критерий                | Оценка                                                                                                                          |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Производительность      | Сам не выполняет chunk-based обработку данных; он оркестрирует задачи, а обработку нужно реализовывать отдельно                 |
| Масштабируемость        | Может масштабироваться для разных задач, но не обработки внутри одной задачи                                                    |
| Надёжность              | Есть retry, schedule, контроль статусов задач                                                                                   |
| Интеграция              | Реализован на Python. Будет сложнее интегрировать с Java, чем Spring Batch                                                      |
| Наблюдаемость           | UI для контроля DAG, истории запусков и ошибок. Но метрики обработки отдельных строк и chunk’ов придётся реализовывать отдельно |
| Микросервисная миграция | Может быть полезен как внешний orchestrator для будущих ETL-процессов и интеграций                                              |
| Простота запуска        | Нужны scheduler, webserver, metadata DB, workers - сложнее чем Spring Batch                                                     |
| Расширяемость           | Хорошо подходит для добавления новых pipeline и зависимостей между ними, но не заменяет саму бизнес-логику обработки данных     |

Хорош на будущее развитие как Оркестратор, но самостоятельно не решает основную задачу - сделать обработку блоками для CSV файлов

### 5.2 Самописный Java Worker

Самописный Java Worker — это отдельный сервис без Spring Batch, который читает CSV, валидирует данные и пишет результат в PostgreSQL. Первое решение, которое придет команде, которая не использует OpenSource, а предпочитает писать сама

| Критерий                | Оценка                                                                                                                   |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Производительность      | Можно реализовать batch insert/update вручную, но всё придётся проектировать самостоятельно                              |
| Масштабируемость        | Можно масштабировать как отдельный сервис, но управление параллелизмом и блокировками нужно реализовывать вручную        |
| Надёжность              | Retry, restart, skip policy, job metadata и восстановление после сбоев придётся писать самостоятельно                    |
| Интеграция              | Хорошо вписывается в Java-стек, потому что это обычный Java-сервис                                                       |
| Наблюдаемость           | Метрики, статусы шагов и логи нужно проектировать и реализовывать вручную                                                |
| Микросервисная миграция | Может быть вынесен из монолита как отдельный сервис                                                                      |
| Простота запуска        | Прост в локальном запуске, но сложность быстро растёт при добавлении production-требований                               |
| Расширяемость           | Новые шаги обработки можно добавлять в коде, но без готовой batch-модели это быстро превращается в самодельный фреймворк |

Самописный Java Worker может быть проще на этапе MVP, но в продакшене это дорогое и рискованное решение

## 6. Последствия

### Положительные

- тяжёлая обработка выносится из монолита
- пользователь не ждёт долгий синхронный запрос
- появляется обработка блоками
- снижается нагрузка на PostgreSQL
- появляются retry/restart и статусы job
- проще собирать метрики и расследовать ошибки
- архитектура становится ближе к микросервисной

### Отрицательные

- появляется новый сервис для сопровождения
- нужно настроить Spring Batch metadata tables
- нужно продумать идемпотентность
- нужно ограничивать параллелизм, чтобы не перегрузить PostgreSQL
